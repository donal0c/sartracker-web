Verdict

The lifecycle ref-counting and the sanitization line-assembly are genuinely well-built. But the PR's headline native fix is untested, and its new change-sequence fence is too strict to survive live tracking. Not mergeable as-is — which is consistent with the PR not requesting merge.

Must fix

1. assertCoverageSnapshotCurrent will reject coverage reads during normal tracking. change_seq is bumped by recordAcceptedCoveragePositions, called from addPosition/addPositionsBulk — the ordinary Traccar ingest path. So any fix landing during a worker run fails the whole readCoverageManifest. On a large mission with multi-second enumeration and several polling devices this can starve indefinitely; the renderer has no backoff and classifies the error as unknown. It also bypasses the ledger's existing graceful snapshotMoved pending path, and the third call site (mission-store.cjs:2331) runs outside any transaction after publication already committed. (I verified the bump path directly.)

2. Callback fan-out has no try/catch — coverage-owner-lifecycle.cjs:22. One synchronous throw becomes an uncaught main-process exception and silently drops cancellation for every remaining in-flight op on that renderer. Reachable: cancelCoverageTileRead is optional in the contract and never existence-checked.

3. The in-snapshot cardinality fix has zero coverage. Deleting it leaves mission-store, IPC, attestation and native-smoke suites all green. Only the parent-side re-read is pinned. assertCoverageSnapshotCurrent also survives per-call-site deletion — enumeration (:2288) is uncovered, and the two manifest sites mutually mask.

4. The shrink-side race is reintroduced. normalizeCoverageOperation now reads limits on the main thread after the worker resolves, so a concurrent delete false-rejects with the generic, non-retryable "item list is invalid". invalidation-analysis is strictly worse than before: a concurrently drained invalidation yields maxAffectedKeys: 0 and a guaranteed hard failure.

Should fix

- isDestroyed() fails open on render-process-gone — Electron keeps it false after a renderer crash, so a queued IPC re-subscribes a once listener that won't fire until the WebContents is actually destroyed, leaving a query uncancelled for potentially the whole window lifetime.
- The new throw sits outside the catalog handler's try, skipping abandonSenderStages/settleAbandonedStages exactly in the case that cleanup exists for; the next sync then fails "already has an unsettled stage".
- Unbounded workerExited join — a worker wedged in a synchronous native SQLite call defeats terminate(), turning the 30s timeout into an open-ended wait that also stalls coverageChunkWorkerTail and prepareClose().
- Multi-byte UTF-8 split corrupts redaction — String(chunk) at packaged-page-diagnostics.js:59 with no setEncoding/StringDecoder on scripts/electron-native-runtime-smoke.mjs:70. A split injects U+FFFD and can break the keyword match that redacts the secret. Tests only feed strings, never Buffers. (Verified.)
- Two green-but-blind smoke paths — stderr?.on yields an evidence-free result: "pass" if the stream is absent; stderr arriving between exit and stream close lands in the receipt after assertNoUnexpectedDiagnostics runs, so a fatal final line can sit inside a pass.
- Concurrent same-sender release ordering untested — making release() detach unconditionally while siblings are in flight stays green. Highest-risk gap, since it orphans SQLite-holding workers on renderer crash.
