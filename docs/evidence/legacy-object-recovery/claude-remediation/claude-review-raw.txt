  ### 2. Moving the poll off-thread makes the `<200ms` gate near-vacuous.
  `tests/unit/electron-mission-evidence-versioning.test.ts:802`

### 6. The diagnostics perturb the very gate their docstring claims not to change.
`tests/support/legacy-object-responsiveness-diagnostics.ts:44`

`heartbeat()` runs synchronously inside the caller's 10ms `setInterval` callback and performs 2× `process.threadCpuUsage`, 2× `process.cpuUsage`, 2× `eventLoopUtilization`, plus two `filter` passes over up to 128 retained spans whenever a new max is set.

The caller (test line 769) stamps `lastHeartbeat = current` using the value sampled at line 766 — *before* that work — so the diagnostic's own duration falls inside the next measured gap and is added to the gated `maximumHeartbeatGapMs`. On a slow runner, the instrumentation added to diagnose the 200ms gate can itself push it red. The line-4 docstring "without changing its clock or gate" is false.

### 7. Nested `finally` blocks mask the original failure with a teardown rejection.
`tests/unit/electron-mission-evidence-versioning.test.ts:791`

If the poll loop throws (assertion, count rejection, timeout) and `await inspection?.close()` at line 791 also rejects — which it will whenever a failure was latched, since `close()` rethrows the retained `failure` at `inspection.ts:324` — the finally's exception wins and the try block's error is discarded. `await diagnostics.finish()` at line 796 can mask both.

CI then reports `Legacy-object inspection close timed out after 5000ms` instead of the operator-meaningful cause.

### 8. `fail()`'s early return latches the generic timeout and discards the worker's real diagnosis.
`tests/support/legacy-object-inspection.ts:140`

The worker's `database.close()` triggers a WAL checkpoint over the 50k-row fixture that exceeds `closeTimeoutMs`; line 304 latches `failure = 'Legacy-object inspection close timed out after 5000ms'` and starts `terminateAndJoin` (setting `terminationRequested`). The worker then posts its real `{type:'error', message:'SQLITE_...'}`, which reaches `fail()` and returns at line 140 without touching `failure`.

`close()` rejects with the generic close error, and the actual SQLite failure is unrecoverable from the test output.

### 9. One transient SQLite error permanently kills the inspector, with no retry and a leaked worker.
`tests/support/legacy-object-inspection-worker.cjs:43`

A per-query error reply omits `requestId`/`threadId`, and the parent's handler at `inspection.ts:184-191` accepts `type:'error'` in any state with no identity or sequence check, routing it straight to `fail()`, which terminates the worker.

A single `SQLITE_BUSY` / `SQLITE_BUSY_SNAPSHOT` from the concurrently-writing backfill worker (or a checkpoint restart) therefore aborts the whole 50k settlement instead of being retried on the next 10ms poll. On that path the worker closes neither `database` nor `parentPort`, so it survives until the parent's terminate lands.

### 10. After a startup failure the worker still registers its message handler with `database` undefined.
`tests/support/legacy-object-inspection-worker.cjs:32`

If `new Database(...)` throws at line 21, the catch posts `{type:'error'}` and calls `parentPort.close()` but does not return, so `parentPort.on('message', ...)` is still registered at line 28. Any count message that reaches it hits `database.prepare(...)` at line 32 with `database === undefined`, throws a TypeError, and the catch at line 42 posts the reply on an already-closed port — a silent no-op in Node. The parent receives nothing and waits out `countTimeoutMs`.

Line 50 already demonstrates the correct optional-chaining guard (`database?.close()`).

### 11. `readonly: true` is an unexamined behaviour change with a platform-sensitive WAL failure mode.
`tests/support/legacy-object-inspection-worker.cjs:21`

The replaced `openDatabase()` (`tests/unit/electron-mission-evidence-versioning.test.ts:4434`) is a plain read-write `new Database(path)`.

A read-only WAL reader requires write access to `<db>-shm`. SQLite's unix VFS falls back to read-only shm when it lacks that, and `walTryBeginRead` can then only read up to an existing read-mark, or returns `SQLITE_READONLY_CANTLOCK`. On a restored CI artifact, a read-only mount, a different uid, or a hot `-wal` left by a killed process, the poll either throws (fatal per finding 9) or pins to a stale snapshot and spins to the timeout reporting 0/50000 — a false failure of a life-safety recovery gate.

### 12. The 4,500-attempt bound was tuned against a synchronous turn and can now exceed the 60s timeout.
`tests/unit/electron-mission-evidence-versioning.test.ts:780`

The deleted comment explicitly stated 4,500 was chosen because "smaller production turns retain current-position priority on slower Linux runners." Each attempt is now `setTimeout(10)` + postMessage + worker query + reply + microtask drain.

On a loaded runner, 4,500 × (10ms + round-trip) exceeds the `60_000ms` timeout at line 805; vitest aborts mid-try, the finally diagnostics at line 798 never print, and the failure reads as a harness timeout rather than `expect(baselineCount).toBe(50_000)`.

### 13. A deliberate 250ms main-thread busy-spin lands in the parallel release-qualification lane; inspectors are not torn down on failure.
`tests/unit/legacy-object-inspection.test.ts:80`

`vitest.config.ts:9` sets `provide: { releaseResponsivenessMode: 'release-qualification' }` but, unlike `vitest.responsiveness.config.ts`, omits `fileParallelism: false`. `npm run test` therefore runs the strict `<200ms` gates in sibling files concurrently with this new 250ms CPU burn, on a machine where vitest already saturates cores — a new cross-file flake source.

Separately, `afterEach` (line 22) only `rm`s the temp dir. Around nine tests hold a live Worker whose `close()`/`terminate()` is on the happy path only, so one mid-test assertion failure leaves a worker thread with an open SQLite handle while its database directory is deleted underneath it.
